# Нагрузочное тестирование и требования к железу

Цель: оценить ресурсы для **100 000** и **1 000 000** одновременных онлайн-игроков и дать методику
реального нагрузочного теста. Документ разделяет **измеренное** (на дев-машине) и **смоделированное**
(экстраполяция с явными допущениями) — без подмены одного другим.

> **Важная оговорка.** 100k/1M одновременных WebSocket-соединений физически не воспроизвести на одной
> машине. Поэтому: (1) удельную стоимость масштаб-критичного яруса (состояние партии) **измерили**
> локально; (2) построили **модель** и экстраполировали; (3) ниже — методика реального E2E-теста на
> staging-кластере с распределёнными генераторами (его нужно прогнать перед запуском). Все формулы
> параметризованы — пересчитайте под свои реальные темп ходов/длину партии после первого прогона.

Архитектура и ярусы — см. [docs/DEPLOYMENT.md](DEPLOYMENT.md). Основной масштаб-таргет (1M) — путь
**онлайн-игры GameServer** (SignalR + Orleans-грейн на партию). Arena (турниры) оценивается отдельно (§8).

---

## 0. Запускаемый калькулятор

Модель ниже реализована как инструмент [tools/capacity](../tools/capacity): `dotnet run --project
tools/capacity -- --players 100000 [--bench]`. Он считает железо под целевое число игроков и (с
`--bench`) замеряет удельные стоимости (ходы/с/ядро, память/партия) на текущей машине. Удобно
пересчитать сайзинг под своё железо/цель без правки этого документа. Математика покрыта тестами
(`CapacityModelTests`). Транспорт/плотность соединений остаются модельными — см. оговорку выше и §6.

## 1. Измеренные удельные стоимости (дев-машина)

Стенд: Apple Silicon, 12 логических ядер, .NET 10 Release, библиотека ходов **Gera.Chess** (та, что в
[GameGrain](../ChessSchool.GameServer/Grains/GameGrain.cs)).

| Метрика | Значение | Примечание |
|---|---|---|
| Обработка ходов | **≈ 6 080 ходов/с на ядро** | консервативно: полная генерация всех легальных ходов + применение. Реальный путь грейна — `IsValidMove(один ход)`, дешевле → это **нижняя граница** |
| Память на активную партию | **≈ 12 КБ** | доска + история ходов (середина партии). С учётом грейна Orleans, строк (sub/имена), часов закладываем **≈ 20 КБ/партию** |

Эти два числа — основа модели для **яруса состояния**. Транспортный ярус (WebSocket/SignalR) и Redis
оцениваем по индустриальным ориентирам (локально 1M соединений не поднять) — помечено как *модель*.

### 1.1 Фактический локальный baseline-прогон (k6 E2E, 1 нода)

Прогон харнеса [tools/loadtest](../tools/loadtest) против локального AppHost: 8 VU → ~4 партии blitz,
ускоренный темп. **Цель — не ёмкость** (нагрузка крошечная, 1 нода, оба игрока на одной ноде = без Redis
backplane), а проверка корректности и **floor задержек**:

| Метрика | Результат | Смысл |
|---|---|---|
| `ws connected (101)` | **100%** (13/13) | auth/handshake/транспорт работают |
| `errors` (отклонённые ходы) | **0** | дебюты-по-gameId легальны, матчмейкинг и стейт-машина верны |
| `match_wait` | p50 **90 мс**, p95 **628 мс** | подбор пары (полный пул — мгновенно) |
| `move_rtt` (submit→broadcast) | p50 **3 мс**, p95 **6 мс**, max **38 мс** | **floor** задержки хода на 1 ноде без backplane |
| `games_matched` | 14 | VU доигрывал и брал новую партию |

Выводы: (1) харнес валиден end-to-end; (2) задержка обработки хода на одной ноде ~единицы мс — далеко
под SLO p95<250 мс; на масштабе её поднимут **Redis backplane** (кросс-нодовые сообщения) и контеншн,
поэтому именно их проверяет staging-тест (§6). `games_finished=0` ожидаемо: синтетические партии не
доходят до мата (60 «срединных» полуходов), завершаются по исчерпанию списка/таймауту.

> Диагностика при первом прогоне: токены сначала отклонялись (401) — классическая грабля #6: GameServer
> валидирует issuer по authority `https://localhost:7139` (Aspire-прокси), а токен был выпущен с
> `iss=…:54602` (порт Kestrel). Лечится выпуском токена через тот же authority-URL, что у сервиса.

## 2. Модель нагрузки (допущения — меняйте под себя)

| Параметр | Значение по умолчанию | Обоснование |
|---|---|---|
| Игроков на партию | 2 | 1M игроков ⇒ **500k** активных партий; 100k ⇒ **50k** |
| Темп ходов на партию | **0.2 полухода/с** (ход раз в ~5 с) | блиц/рапид вперемешку; пик активной фазы |
| Средняя длительность партии | **5 мин** | блиц 3+2 / рапид; для темпа завершений |
| Размер сообщения хода | **≈ 0.5 КБ** JSON | `GameStateDto`: FEN + часы + имена |
| Соединений WebSocket на ноду | **≈ 50 000** *(модель)* | настроенный Kestrel/SignalR; зависит от RAM/fd/CPU |
| Память на WS-соединение | **≈ 30 КБ** *(модель)* | буферы + контекст SignalR; тюнингуется |

Производные величины:

```
активные_партии        = игроки / 2
ходов/с (кластер)      = активные_партии × 0.2
завершений/с           = активные_партии / (длительность_с)
ядра_на_ходы           = ходов_в_с / 6080            (нижняя граница; ×2–3 на оверхед фреймворка)
память_состояния       = активные_партии × 20 КБ
память_соединений      = игроки × 30 КБ
ноды_по_соединениям    = игроки / 50 000
```

## 3. Ресурсная модель по ярусам

### 3.1 GameServer (транспорт SignalR + силос Orleans) — главный ярус

- **Соединения:** по 1 WS на игрока. Лимитирует плотность на ноду (≈50k) → определяет число нод.
- **Память:** состояние партий (≈20 КБ × партии) + соединения (≈30 КБ × игроки) + рантайм .NET/Orleans.
  Доминируют **соединения**.
- **CPU:** обработка ходов (измерено) **+** транспорт (TLS, фрейминг WS, сериализация SignalR) — на
  практике транспорт/сериализация ≥ шахматной логики. Закладываем компанию ×2–3 к «ядрам_на_ходы».
- **Grain storage:** `GameGrain` **не персистится** (в RAM только активные партии) → нет записи в Redis
  на ход. Это сознательно ради масштаба (см. CLAUDE.md): при падении ноды недоигранные партии теряются
  (редко, партии короткие), завершённые — архивируются в Postgres.

### 3.2 Redis (SignalR backplane + Orleans clustering) — узкое место №1

- **Backplane:** каждый ход → рассылка в группу `gameId`. Если игроки на **разных** нодах (вероятно при
  шардировании соединений) — сообщение идёт через Redis. ⇒ ≈ `ходов/с` публикаций в Redis.
- **Clustering:** членство силосов — лёгкое.
- Вывод: при 1M это **сотни тысяч pub/sec** → нужен **Redis Cluster** (шардирование) либо устранение
  backplane для внутриигровых сообщений (см. §7 — co-location игроков партии на одной ноде).

### 3.3 PostgreSQL — запись при завершении

- Архивация партии + пересчёт рейтинга + точки рейтинга на каждое `завершений/с`.
- Профильные чтения (родители/ЛК) — на реплики. Партиционировать `Games` по дате.

### 3.4 Stateless (Auth / ApiService / Web)

- Масштабируются по RPS. Пики Auth — на логине (выпуск токенов). ApiService принимает архивацию от
  GameServer (внутр.).

## 4. Требования к железу — 100 000 игроков

Производные: 50k партий; ходов/с ≈ **10 000**; завершений/с ≈ **167**; ядра_на_ходы ≈ 1.6 (→ ~4–5 с оверхедом).

| Компонент | Размер | Обоснование |
|---|---|---|
| **GameServer** | **3–4 ноды × 8 vCPU / 16 ГБ** | 100k/50k ≈ 2 ноды по соединениям + запас на отказ/пики |
| **Redis** | 1 primary + 1 replica, 4 vCPU / 8 ГБ | ≈10k pub/sec — в пределах одного инстанса |
| **PostgreSQL** | primary 8 vCPU / 32 ГБ + 1 read-replica | ≈167 записей/с — комфортно |
| **Auth** | 2–3 пода × 2 vCPU / 2 ГБ | пики логина |
| **ApiService** | 3 пода × 2 vCPU / 4 ГБ | приём архивации + чтения |
| **Web** | 2–3 пода × 2 vCPU / 4 ГБ | SSR |

Память GameServer-фронта: соединения 100k×30КБ ≈ **3 ГБ** + состояние 50k×20КБ ≈ **1 ГБ** + рантайм — на
3–4 ноды по 16 ГБ с большим запасом.

---

## 5. Требования к железу — 1 000 000 игроков

Производные: 500k партий; ходов/с ≈ **100 000**; завершений/с ≈ **1 667**; ядра_на_ходы ≈ 16 (→ ~40–60 с оверхедом).

| Компонент | Размер | Обоснование |
|---|---|---|
| **GameServer** | **24–30 нод × 8 vCPU / 16 ГБ** (≈200–240 vCPU) | 1M/50k = 20 нод по соединениям + запас на отказ/GC/пики |
| **Redis** | **Redis Cluster: 3–6 шардов** (каждый +replica), 8 vCPU / 16 ГБ | ≈100k+ pub/sec backplane — обязательно шардирование |
| **PostgreSQL** | primary 16 vCPU / 64 ГБ + 2–3 read-replicas, партиционирование `Games` | ≈1 700 записей/с + профильные чтения; батчинг архивации |
| **Auth** | 6–10 подов × 2–4 vCPU | пики логина при массовом онлайне |
| **ApiService** | 10–16 подов × 2–4 vCPU | ≈1 700 архиваций/с от GameServer |
| **Web** | 8–16 подов × 2–4 vCPU | SSR-трафик |

Память GameServer-фронта: соединения 1M×30КБ ≈ **30 ГБ** + состояние 500k×20КБ ≈ **10 ГБ** + рантайм —
распределяется по 24–30 нодам (≈1.5–2 ГБ/ноду), с запасом на 16 ГБ.

> Числа — инженерная оценка от измеренного floor’а и индустриальных ориентиров плотности соединений.
> **Перед продом обязателен реальный E2E-тест (§6)** — плотность WS/ноду и CPU транспорта сильно зависят
> от тюнинга Kestrel, размера сообщений и сети; именно они, а не шахматная логика, двигают число нод.

## 6. Методика реального нагрузочного теста (staging)

Нельзя мерить с одной машины — нужны **распределённые генераторы** (несколько load-нод или k6 Cloud),
бьющие по staging-кластеру, идентичному проду (Redis Cluster, Postgres, N нод GameServer).

**Что измерять (SLO-ориентиры):**
- p50/p95/p99 **задержки хода** (от отправки до получения соперником) — цель p99 < 150–250 мс;
- плотность **WS-соединений на ноду** до деградации;
- **CPU/RAM на ноду**, GC-паузы;
- **Redis** pub/sec, CPU, задержка;
- **Postgres** записи/с, задержка архивации, лаг реплик;
- частота ошибок/реконнектов.

**Профиль нагрузки:** ramp-up соединений (например, +5k/мин), каждая пара играет партию со средним
темпом 0.2 полухода/с; держать плато; наращивать до нарушения SLO → это и есть ёмкость на ноду.

**Авторизация:** `/gamehub` требует JWT (валидация IdP). Для теста: прогнать OIDC (authorization
code + PKCE) для пула тестовых пользователей и переиспользовать access-токены, либо в **изолированном
staging** временно включить тестовый аудитор токенов. Не отключать auth на проде.

**Каркас k6** (xk6-websockets; токен подставляется заголовком при negotiate):

```javascript
import ws from 'k6/ws';
import { check } from 'k6';
export const options = {
  scenarios: { ramp: { executor: 'ramping-vus', startVUs: 0,
    stages: [{ duration: '5m', target: 20000 }, { duration: '15m', target: 20000 }] } },
};
export default function () {
  const token = __ENV.TOKEN; // выдать заранее на пул тест-юзеров
  const url = `${__ENV.HUB}/gamehub?access_token=${token}`;
  ws.connect(url, {}, (socket) => {
    socket.on('open', () => {
      socket.send(JSON.stringify({ protocol: 'json', version: 1 }) + ''); // SignalR handshake
      socket.send(JSON.stringify({ type: 1, target: 'FindMatch', arguments: [180, 2] }) + '');
    });
    socket.on('message', () => { /* on GameState: отправить следующий ход с задержкой ~5с */ });
    socket.setTimeout(() => socket.close(), 300000);
  });
}
```

(Полная реализация ведёт стейт-машину партии: дождаться пары → слать легальные ходы по таймеру →
мерить RTT. Запускать с N load-нод, агрегировать в k6 Cloud/Grafana.)

## 7. Узкие места и рычаги масштабирования

1. **Backplane Redis (главное).** При шардировании соединений оба игрока партии обычно на разных нодах →
   почти каждый ход идёт через Redis. **Рычаг:** маршрутизировать обоих игроков партии на **одну ноду**
   (sticky по `gameId`/матчмейкингу) — внутриигровые сообщения остаются локальными, backplane разгружается
   на порядок. Сильнейшая оптимизация для 1M.
2. **Плотность WS/ноду.** Тюнинг Kestrel (лимиты, буферы), размер сообщений (минимизировать DTO), сжатие.
   Прямо определяет число нод.
3. **Боты Arena (Stockfish).** Каждый ход бота — вызов Stockfish (CPU-тяжёлый, сериализуется семафором,
   [StockfishEngine](../ChessSchool.Arena/Services/StockfishEngine.cs)). Масса бот-партий = CPU-боттлнек.
   **Рычаг:** пул процессов/ограничение силы/доля ботов; боты — для наполнения, не для масштаба.
4. **Архивация в Postgres.** Батчинг записей, партиционирование `Games`, чтения на реплики.
5. **GameGrain без персиста** — осознанный размен (масштаб RAM ↔ потеря недоигранной партии при падении
   ноды). Если нужна durability — чаще архивировать/персистить ключевые вехи (ценой нагрузки на стор).

---

## 8. Arena (турниры) — отдельно

Arena масштабируется не «общим числом игроков», а **числом и размером одновременных турниров**: каждый
турнир — один грейн с таймером 500 мс ([ArenaGrains](../ChessSchool.Arena/Grains/ArenaGrains.cs)), который
ведёт все свои доски. Боттлнеки: CPU таймеров активных турниров и **Stockfish** для бот-партий. Для
крупных турниров — горизонтально по силосам (грейн-на-турнир балансируется кластером); боты — с пулом и
лимитом. Отдельный нагрузочный сценарий: K одновременных турниров × M участников, рост до деградации тика.

## 9. Итог

- **100k:** ~3–4 ноды GameServer (8 vCPU/16 ГБ), 1 Redis (+replica), 1 Postgres (+replica), по 2–3 пода
  stateless. Запас большой.
- **1M:** ~24–30 нод GameServer, **Redis Cluster** (3–6 шардов), Postgres 16 vCPU + реплики, 8–16 подов
  stateless. Главный риск — **backplane Redis**; ключевой рычаг — **co-location игроков партии**.
- Числа состояния — измерены; транспорт/соединения — модель, **обязательна валидация E2E-тестом (§6)**
  на staging до прод-запуска.
