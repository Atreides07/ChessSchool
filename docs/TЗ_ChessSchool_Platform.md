# ТЗ: Платформа ChessSchool (на базе idchess)

> Версия 0.1 (черновик для разработки). Дата: 2026-06-24.
> Назначение документа: техническое задание для команды/ИИ-разработчика на создание веб-платформы и бэкенда продукта для шахматных школ, к которому подключается модифицированное мобильное приложение idchess.

---

## 1. Назначение и бизнес-контекст

Продукт позволяет шахматным школам:
- автоматически сохранять тренировочные партии учеников (запись и распознавание ходов делает мобильное приложение idchess);
- вести таблицу учеников в личном кабинете (ЛК) школы;
- считать внутришкольный рейтинг ученика и показывать его динамику на графике;
- давать родителю ссылку на профиль ребёнка (прогресс, рейтинг, партии) без сложной регистрации.

Ключевой архитектурный принцип: **сервис авторизации выделен в отдельный продукт-независимый компонент (Identity Provider)**, который в будущем подключается к другим продуктам компании по модели «как Google Auth».

### Основной пользовательский сценарий MVP — тренировочные партии
Ученики на занятии свободно садятся за доски; пары заранее не заданы. Мобильное приложение idchess записывает партию за конкретной доской/устройством, а привязка партии к двум ученикам и цветам выполняется через **чек-ин в приложении** (см. раздел 8).

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **IdP / Auth Service** | Отдельный сервис авторизации (OAuth 2.0 / OpenID Connect), выдаёт токены, общий для нескольких продуктов |
| **ChessSchool Backend** | Бэкенд продукта (школы, ученики, партии, рейтинг, шаринг) |
| **Mobile App** | Модифицированное приложение idchess: запись партии, распознавание ходов, чек-ин |
| **Student** | Ученик (профиль), может быть несовершеннолетним |
| **Attribution / Атрибуция** | Привязка записанной партии к двум ученикам и их цветам |
| **Check-in / Чек-ин** | Действие ученика/тренера в приложении: «за этой доской играют X (белые) и Y (чёрные)» |
| **Share link** | Ссылка-токен на read-only профиль ученика для родителя |

## 3. Архитектура системы

```
                       ┌─────────────────────────┐
                       │   Auth Service (IdP)     │  ← отдельный продукт
                       │  OAuth2 / OIDC, JWT,     │
                       │  users, clients, scopes  │
                       └───────────┬──────────────┘
                                   │ OIDC (access/refresh token)
        ┌──────────────────────────┼───────────────────────────┐
        │                          │                            │
┌───────▼────────┐        ┌────────▼─────────┐         ┌────────▼────────┐
│  Web (ЛК школы)│        │ ChessSchool API   │◄────────│  Mobile App      │
│  React/Next    │◄──────►│ Go (Fiber)        │  REST   │  (idchess mod.)  │
│  админка       │  REST  │ PostgreSQL+Redis  │         │  запись+чек-ин   │
└────────────────┘        └────────┬──────────┘         └─────────────────┘
                                   │
                          ┌────────▼──────────┐
                          │  Rating Engine     │ (Glicko-2)
                          │  Attribution Svc   │
                          └────────────────────┘
                                   │
                          ┌────────▼──────────┐
                          │  Share-link сервис │ → публичный read-only профиль
                          └────────────────────┘
```

### Компоненты
1. **Auth Service (IdP)** — отдельный деплой и репозиторий. Не знает о шахматах. Управляет пользователями, клиентами (приложениями), выдаёт и валидирует токены.
2. **ChessSchool Backend** — бизнес-логика продукта. Доверяет токенам IdP, хранит доменные данные.
3. **Web (ЛК школы)** — SPA для админов и тренеров.
4. **Mobile App** — поставляет партии и чек-ины через API.
5. **Share-link сервис** — выдаёт родителю доступ к профилю ученика по токену.

### Рекомендуемый стек (под стандарты Friflex)
- **Backend / Auth:** Go + Fiber, PostgreSQL, Redis, JWT.
- **Mobile:** Flutter (модификация idchess).
- **Web:** React + Next.js (богатая экосистема админок) — допустимо Flutter Web, если нужна единая кодовая база с мобильным.
- **Инфраструктура:** Docker, миграции БД, CI с прогоном тестов и линтера.

## 4. Сервис авторизации (IdP) — отдельный, переиспользуемый

> Главное требование заказчика: авторизация = отдельный сервис, подключаемый к разным продуктам в будущем (аналог Google Auth).

### 4.1 Стандарты
- Реализует **OAuth 2.0 + OpenID Connect (OIDC)**.
- Поддерживает grant types: `authorization_code` (с PKCE — для web и mobile), `refresh_token`, `client_credentials` (для server-to-server).
- Выдаёт **JWT** access-токены (короткоживущие, 15 мин) и refresh-токены (долгоживущие, ротация).
- Публикует `/.well-known/openid-configuration` и JWKS (`/.well-known/jwks.json`) — продукты валидируют подпись токена по публичному ключу, не обращаясь к IdP на каждый запрос.

### 4.2 Мультипродуктовость
- Сущность **Client (Application)**: каждый продукт регистрируется как client (`client_id`, `client_secret`, redirect URIs, разрешённые scopes).
- **Scopes / audiences** позволяют одному пользователю иметь доступ к нескольким продуктам с разными правами.
- Пользователь един для всех продуктов (single account), но роли — на стороне продукта (ChessSchool сам решает, что этот user = тренер школы N).

### 4.3 Функции
- Регистрация / вход по email + пароль (хеш — Argon2id / bcrypt).
- Подтверждение email, сброс пароля.
- (Опционально, фаза 2) Социальный вход (Google/VK/Apple) и магик-линки.
- Управление сессиями и устройствами, отзыв refresh-токенов.
- Базовый профиль пользователя (имя, email, аватар).

### 4.4 Безопасность
- PKCE обязателен для публичных клиентов (mobile/web SPA).
- Rate limiting на логин и сброс пароля.
- Ротация и инвалидция refresh-токенов (detect reuse).
- Хранение секретов вне кода; **никогда не читать `.env`** — имена нужных переменных запрашиваются у владельца проекта, шаблон ведётся в `env.example`.
- Аудит-лог событий входа.

### 4.5 Контракт для продуктов
ChessSchool Backend:
1. Принимает access-токен в заголовке `Authorization: Bearer`.
2. Валидирует подпись по JWKS, проверяет `aud`, `exp`, `iss`.
3. Извлекает `sub` (стабильный ID пользователя) и маппит на свою сущность `User`/`Coach`/`Admin`.

## 5. ChessSchool Backend — функциональные требования

### 5.1 Управление школой
- CRUD школы (для супер-админа / онбординга).
- CRUD групп внутри школы.
- Приглашение тренеров (по email через IdP).

### 5.2 Таблица учеников (ядро ЛК)
- CRUD ученика: имя/псевдоним, дата рождения, группа, заметка тренера.
- Привязка ученика к родителю (через share-link, без обязательной регистрации родителя в MVP).
- Поля рейтинга: текущий рейтинг, RD, число партий, % результатов.
- Сортировка/фильтр/поиск по таблице; сортировка по рейтингу, активности.
- Статус согласия на обработку ПДн (см. раздел 11).

### 5.3 Партии
- Приём партий из мобильного приложения (PGN, результат, тайминги, board/device, видео-реплей если есть).
- Идемпотентность приёма (по `idchess_game_id`).
- Статусы партии: `pending` → `attributed` → `disputed`.
- Очередь «Требуют атрибуции» для тренера.
- Реплей партии в вебе (доска + перемотка ходов).

### 5.4 Атрибуция (тренировочный сценарий) — см. раздел 8.

### 5.5 Рейтинг
- Алгоритм **Glicko-2**, отдельный внутришкольный рейтинг (FIDE — опциональное справочное поле).
- В рейтинг идут только партии со статусом `attributed` и `is_rated=true`.
- Ретро-пересчёт истории при исправлении атрибуции тренером (идемпотентно).
- История рейтинга для графика (точки во времени + привязка к партиям).

### 5.6 Шаринг профиля родителю — см. раздел 7.

## 6. Веб-приложение (ЛК школы)

### Разделы
1. **Дашборд школы** — сводка: число учеников, активность, недавние партии.
2. **Ученики** — таблица (см. 5.2), карточка ученика (рейтинг, график, список партий, кнопка «Поделиться с родителем»).
3. **Группы** — управление группами и тренерами.
4. **Очередь атрибуции** — список партий без привязки, быстрый UI назначения (доска, время, превью → выбрать 2 учеников и цвета в пару тапов).
5. **Партия** — просмотр/реплей, переназначение игроков, флаг «спорная».
6. **Настройки школы** — тариф, согласия, интеграции.

### Требования к UX
- Атрибуция одной партии ≤ 2–3 действий тренера.
- График рейтинга: фильтр по периоду, маркеры партий.
- Адаптивность (тренеры часто с планшета/телефона).

## 7. Шаринг профиля ученика родителю

Требование: тренер даёт родителю ссылку на профиль ребёнка.

### Механика
- Тренер в карточке ученика жмёт «Поделиться» → генерируется **share link** с токеном.
- Ссылка ведёт на **read-only публичную страницу профиля** ученика: текущий рейтинг, график динамики, число партий, % побед/ничьих/поражений, последние партии с реплеем.
- Доступ ограничен: токен непредсказуемый (UUID/случайный), может иметь срок жизни и возможность отзыва тренером.
- (Фаза 2) Родитель может «закрепить» ссылку за своим аккаунтом IdP → личный кабинет родителя с несколькими детьми и уведомлениями.

### Приватность
- Публичная страница не раскрывает ПДн соперников (анонимизация / только псевдонимы).
- Показ только при наличии согласия родителя на обработку ПДн ребёнка.
- Возможность отзыва ссылки и удаления данных.

## 8. Интеграция с мобильным приложением и атрибуция

### 8.1 Поток данных
1. Тренер/ученик в приложении выбирает доску/устройство и **делает чек-ин**: кто играет белыми, кто чёрными (выбор из списка учеников группы или скан QR-бейджа ученика).
2. Приложение записывает партию, распознаёт ходы, формирует PGN + результат + тайминги.
3. По завершении отправляет партию в ChessSchool API вместе с данными чек-ина.
4. Backend связывает партию с двумя учениками и цветами → статус `attributed` (high confidence).

### 8.2 Слой Identity Resolution
- Разделяем сущности **Device/Board**, **BoardSession** (интервал занятости пары), **Student**.
- Партия матчится к BoardSession по времени и устройству; из сессии берутся ученики и цвета.
- Пересадка учеников меняет BoardSession, а не личность.

### 8.3 Краевые случаи (обязательны)
- **Нет чек-ина** → партия в очередь «Требуют атрибуции», `pending`, в рейтинг не идёт.
- **Низкая уверенность** → не влияет на рейтинг до подтверждения тренером.
- **Соперник — не ученик / тренер** → слот «Гость», партия нерейтинговая (настраивается).
- **Перепутаны цвета** → проверка/флаг, ручная правка.
- **Замена игрока в середине** → пометка `disputed`, ручная проверка.
- Любую авто-атрибуцию тренер может переопределить (с аудитом и ретро-пересчётом рейтинга).

## 9. Модель данных (основные сущности)

> Доменные данные — в ChessSchool Backend. Учётные записи — в IdP (ссылка по `sub`).

- **School** (id, name, plan)
- **Group** (id, school_id, coach_user_sub, schedule)
- **CoachMembership** (user_sub, school_id, role)
- **Student** (id, group_id, display_name, birth_date, note, consent_status, fide_rating?)
- **ParentLink** (id, student_id, parent_user_sub?, share_token, expires_at, revoked)
- **Device** (id, school_id, idchess_device_ref)
- **BoardSession** (id, device_id, started_at, ended_at, source: checkin/manual, white_student_id, black_student_id, confidence)
- **Game** (id, idchess_game_id UNIQUE, device_id, started_at, ended_at, pgn, result, status, replay_url?)
- **GameParticipation** (id, game_id, student_id, color, is_rated, opponent_type)
- **RatingHistory** (id, student_id, rating, rd, sigma, date, game_id)
- **AttributionEvent** (id, game_id, method, actor_user_sub, before, after, created_at) — аудит
- **ConsentRecord** (id, student_id, type, granted_by, granted_at, revoked_at?)

## 10. API (ключевые эндпоинты, черновик)

> Все защищённые маршруты — Bearer JWT от IdP.

**Auth (IdP):**
- `GET /.well-known/openid-configuration`
- `GET /.well-known/jwks.json`
- `POST /oauth/token`
- `GET /oauth/authorize`
- `POST /register`, `POST /password/reset`

**ChessSchool — школа/ученики:**
- `GET /schools/{id}/students` — таблица учеников (с фильтрами)
- `POST /schools/{id}/students`
- `GET /students/{id}` — карточка + рейтинг
- `GET /students/{id}/rating-history` — точки для графика
- `GET /students/{id}/games`

**Партии и атрибуция:**
- `POST /ingest/games` — приём партии из mobile (идемпотентно по idchess_game_id)
- `POST /devices/{id}/checkin` — чек-ин пары на доску
- `GET /schools/{id}/games?status=pending` — очередь атрибуции
- `POST /games/{id}/attribute` — назначение игроков/цветов (триггерит пересчёт рейтинга)
- `POST /games/{id}/dispute`

**Шаринг:**
- `POST /students/{id}/share` — создать share-link
- `GET /share/{token}` — публичный read-only профиль
- `DELETE /share/{token}` — отзыв

## 11. Безопасность и приватность (дети — критично)

- **152-ФЗ / GDPR**: явное согласие родителя на обработку ПДн ребёнка и видеосъёмку **до** записи. Без согласия — профиль не публикуется, ссылка не работает.
- **Биометрия (распознавание лиц) не используется** для идентификации в MVP.
- Минимизация ПДн: для атрибуции достаточно псевдонима + ID.
- Изоляция доступа: тренер — только свои группы; родитель — только своего ребёнка; анонимизация соперников на публичной странице.
- Право на отзыв согласия и удаление данных (включая видео и share-link).
- Секреты — вне репозитория; **`.env` не читать**; шаблон — `env.example`.

## 12. Нефункциональные требования

- Идемпотентный приём партий (нет дублей).
- Аудит всех изменений атрибуции и рейтинга.
- Целевые SLA атрибуции: ≥80% тренировочных партий атрибутируются автоматически (через чек-ин) без ручной правки.
- Масштаб: десятки школ × десятки устройств × тысячи партий/мес.
- Покрытие тестами бизнес-логики (атрибуция, рейтинг) и контрактных API; прогон тестов и линтера в CI.

## 13. Этапы (MVP → дальше)

**MVP:**
1. Auth Service (OIDC, email+пароль, JWT, мультиклиентность).
