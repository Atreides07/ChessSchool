# ADR-0001: Co-location обоих игроков партии на одной ноде GameServer

**Статус:** Предложено (не принято — реализация за фиче-флагом, включение в проде гейтится staging-тестом)
**Дата:** 2026-06-28
**Принимающие:** владелец GameServer / платформенная команда
**Связано:** [CAPACITY_PLANNING.md §7](../CAPACITY_PLANNING.md) (узкое место №1), [DEPLOYMENT.md](../DEPLOYMENT.md)

## Контекст

Целевой масштаб онлайн-игры — до **1M** одновременных игроков (≈500k активных партий, ≈100k
ходов/с по кластеру). Текущий путь хода:

1. Браузерный SignalR подключается к **одному** сервисному URL GameServer → балансировщик кидает
   соединение на произвольную ноду ([Play.razor](../../ChessSchool.Web/Components/Pages/Play.razor)).
2. `FindMatch` → `MatchmakingGrain` (ключ = контроль времени) сводит пару, но соединения двух
   игроков **остаются на тех нодах, куда их назначил LB** ([GameHub.cs](../../ChessSchool.GameServer/Hubs/GameHub.cs)).
3. `Move` → `Clients.Group(gameId).SendAsync("GameState", …)`. Группа `gameId` обычно распределена
   по **двум разным нодам** → рассылка идёт через **Redis backplane на каждый ход**.

При шардировании соединений почти каждый ход проходит через Redis. На 1M это **сотни тысяч
pub/с** → обязателен Redis Cluster (3–6 шардов), и Redis становится узким местом №1.

**Силы:**
- Снизить нагрузку на backplane на порядок (главный рычаг к 1M по capacity-плану).
- Не сломать надёжность: реконнект при плохой сети, отказ/масштабирование нод (churn), краевые
  случаи матчмейкинга.
- Не переизобретать проверенные компоненты (SignalR Redis backplane, Orleans clustering).
- Выигрыш проявляется **только на мультинодовом кластере** — локально (одна нода в Aspire) его
  нельзя измерить, можно проверить лишь **корректность** и безопасную деградацию.

### Ключевое техническое ограничение (часто упускают)

Co-location соединений **сама по себе не убирает publish в Redis.** SignalR с `AddStackExchangeRedis`
публикует групповые/адресные сообщения в Redis **независимо** от того, локальны ли получатели:
менеджер жизненного цикла — Redis-овый, он не короткозамыкает локальную доставку. Значит выигрыш
реализуется, только если для co-located партий доставка идёт **мимо backplane** (локальный путь).
Любой выбранный вариант обязан решить и (1) посадку обоих соединений на одну ноду, и (2)
локальную доставку без round-trip в Redis.

## Решение

Целевой прод-вариант — **Option B (consistent-hash на L7-ингрессе по `gameId`) + local-first
доставка** для co-located партий, **за фиче-флагом `GameServer:Colocation:Enabled` (по умолчанию
off)**. Off → текущее поведение (один URL, group-рассылка через backplane) без изменений.
Включение в проде — только после прохождения staging E2E-теста ([CAPACITY_PLANNING §6](../CAPACITY_PLANNING.md)),
доказавшего падение pub/с backplane и p99 хода в рамках SLO при churn нод.

Если инфраструктура не может дать per-game маршрутизацию — запасной чисто-кодовый путь
**Option C (Orleans-маршрутизируемая адресная доставка)**.

## Рассмотренные варианты

### Option A: SignalR negotiate-redirect + поимённая адресуемость нод

Матчмейкинг выбирает хост-ноду партии (consistent hash `gameId` по членству силосов Orleans);
кастомный negotiate возвращает клиенту `{url: <конкретная нода>, accessToken}` → клиент
переподключается к назначенной ноде.

| Измерение | Оценка |
|---|---|
| Сложность | Высокая |
| Инфра-связность | Высокая (каждая нода адресуема: headless-service / per-pod ingress) |
| Масштабируемость | Высокая |
| Знакомость команде | Средняя (документированный, но редкий паттерн) |

**Плюсы:** прямой контроль посадки; стандартный механизм SignalR.
**Минусы:** redirect — лишний round-trip и источник реконнект-штормов при churn; «ждущий игрок»
ещё не знает `gameId` → матчмейкинг приходится выносить из игрового сокета; всё ещё нужен
local-first путь доставки (ограничение выше).

### Option B: Consistent-hash на ингрессе по `gameId` (рекомендуемый)

Двухфазный клиент: **фаза 1 — матчмейкинг** (короткий HTTP/SignalR на любую ноду) отдаёт
`gameId`+цвет; **фаза 2 — игровой сокет** открывается на URL с ключом `gameId`, L7-ингресс
(Envoy/nginx `hash`, k8s consistent-hash) маршрутизирует по этому ключу → оба игрока одной партии
(один `gameId`) попадают на **одну ноду**. Игровой трафик (все ходы) — во второй фазе, поэтому
co-location там, где она нужна. Локальная доставка — local-first (см. ниже).

| Измерение | Оценка |
|---|---|
| Сложность | Средняя (код приложения умеренный, основная сложность — конфиг ингресса) |
| Инфра-связность | Средняя (consistent-hash upstream; ноды не обязаны быть поимённо адресуемы) |
| Масштабируемость | Высокая |
| Знакомость команде | Высокая (обычный L7-роутинг) |

**Плюсы:** SignalR и Orleans почти не трогаем (минимум переизобретения); тяжёлую часть берёт
проверенный ингресс; **безопасная деградация** — если ингресс не co-locate (rebalance ключей при
churn), партия просто работает через backplane, как сегодня; матчмейкинг-сокет короткий и лёгкий.
**Минусы:** требуется двухфазный клиент; ребаланс хеш-кольца при добавлении/удалении нод временно
рассаживает часть активных партий по разным нодам (деградирует в текущее поведение, не ломается);
нужен local-first путь доставки.

### Option C: Orleans-маршрутизируемая адресная доставка (запасной, чисто код)

Отказ от `Clients.Group` для игровых сообщений. Реестр `connection→silo` (грейн по `sub`/`gameId`),
`GameGrain` знает обоих игроков и доставляет «GameState» только на силосы их соединений через
per-silo грейн + локальный `IHubContext`. Co-located партия = одна локальная отправка, ноль Redis;
не-co-located = адресная доставка на 2 силоса вместо group-pub/sub.

| Измерение | Оценка |
|---|---|
| Сложность | Высокая (фактически свой адресный backplane) |
| Инфра-связность | Низкая (чистый код, без изменений ингресса) |
| Масштабируемость | Высокая, если реестр и доставка сделаны без гонок |
| Знакомость команде | Низкая |

**Плюсы:** без инфра-изменений; выигрыш от co-location «бесплатный», плюс адресная (не
веерная) доставка даже без co-location; полный контроль.
**Минусы:** переизобретение проверенного backplane (риск тонких багов на reconnect/churn/гонках
реестра); выше нагрузка на сопровождение; реестр соединений — новый распределённый стор-путь.

### Option D: Статус-кво (group + Redis Cluster)

Ничего не co-locate, абсорбируем pub/с шардированным Redis Cluster (capacity-план уже это
закладывает на 1M).

| Измерение | Оценка |
|---|---|
| Сложность | Нулевая (уже так) |
| Инфра-связность | Низкая (но дорогой Redis Cluster) |
| Масштабируемость | Ограничена пропускной способностью backplane; дороже по железу |
| Знакомость команде | Полная |

**Плюсы:** ноль работы и риска; уже валидно. **Минусы:** Redis — постоянное узкое место и статья
расходов на 1M; не снимает рычаг, обозначенный в capacity-плане.

## Анализ trade-offs

- **A против B:** оба сажают соединения на одну ноду, но A требует поимённой адресуемости нод и
  redirect-round-trip (хрупко при churn). B перекладывает маршрутизацию на проверенный L7 и
  деградирует безопасно. B предпочтительнее по надёжности и меньшему переизобретению.
- **B против C:** B минимально трогает приложение, но связан с инфраструктурой (ингресс) и всё
  равно требует local-first доставки. C не трогает инфраструктуру, но строит свой адресный
  backplane (риск/сопровождение). При наличии управляемого L7 — B; если ингресс не умеет
  per-game hash — C.
- **Против D:** D — честный «не делать сейчас». Допустим до 100k (Redis с запасом). К 1M рычаг
  co-location экономит железо Redis и снимает узкое место; цена — сложность B/C.
- **«Измерь сначала».** Выигрыш не наблюдаем на одной ноде. Поэтому реализация **обязана** быть за
  флагом и off по умолчанию, а включение — после staging-теста, измеряющего pub/с и p99 при churn.

## Последствия

**Станет проще:** масштабирование к 1M без линейного роста Redis-кластера; внутриигровые сообщения
co-located партий — локальные (единицы мс, без сетевого hop’а).

**Станет сложнее:** клиент становится двухфазным (матчмейкинг отдельно от игрового сокета);
появляется конфиг ингресса (B) или реестр соединений (C); нужен local-first путь доставки и его
fallback на backplane; обработка ребаланса хеш-кольца при churn нод.

**Что пересмотреть:** после staging-теста — фактическая плотность WS/ноду и доля co-located партий
при реальном churn; решение A/B/C финализируется по данным теста (сейчас рекомендация — B).
