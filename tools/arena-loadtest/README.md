# Нагрузочный тест Арены (ярус грейна)

Измеряет масштабируемость **грейна турнира** (единица масштабирования Арены — грейн-на-турнир,
single-writer) под синтетической нагрузкой участников. Модель ёмкости и требования к железу —
[../../docs/CAPACITY_PLANNING.md](../../docs/CAPACITY_PLANNING.md) §8.

## Почему на ярусе грейна, а не через SignalR-хаб
`ArenaHub` аутентифицируется по **cookie-сессии** → 5000 реальных клиентов потребовали бы 5000
OIDC-логинов, и на одной машине мы мерили бы **генератор нагрузки**, а не Арену (та же оговорка, что в
[CAPACITY_PLANNING §0/§8](../../docs/CAPACITY_PLANNING.md) про невоспроизводимость транспорта локально).
Поэтому здесь честно измеряется то, что **можно** измерить на одной машине: стоимость состояния и тика
грейна турнира. Транспортный ярус (WS/SignalR-плотность, Redis-backplane) — по §6 (staging).

## Как работает
Поднимает in-proc Orleans-силос (тот же `TestClusterBuilder`, что в `ChessSchool.Tests`): память-хранилище
`arena`, заглушка движка (бот ходит случайным легальным — Stockfish не нужен), reminders off, реальное
время. Боты выключены (`SetCountAsync(...,0)`) — изолируем нагрузку **людей**.

## Запуск
```bash
dotnet run -c Release --project tools/arena-loadtest -- --players 5000 --sustain-seconds 15
# 10 000 активно играющих:
dotnet run -c Release --project tools/arena-loadtest -- --scenario play --players 10000 --sustain-seconds 20
# --scenario storm|horizontal|sustain|play|all (по умолчанию all)
```
Docker не нужен (силос in-proc). Прогон ~1–2 мин.

## Сценарии
1. **Шторм в один грейн** (`storm`) — регистрация+подбор N участников в ОДНОМ турнире; стоимость одного тика
   при росте населения.
2. **Горизонтально по грейнам** (`horizontal`) — те же N, распределённые по K турнирам; агрегатная пропускная
   способность (грейн-на-турнир исполняется параллельно) — рычаг масштабирования Арены.
3. **Устойчивый тик** (`sustain`) — N/2 живых партий, окно T секунд; проба `GetSummary` каждые 250 мс мерит
   round-trip за тиком → отзывчивость грейна под нагрузкой (бюджет тика 500 мс).
4. **Активная игра** (`play`) — N игроков РЕАЛЬНО играют: харнес волнами гонит ходы через `MoveAsync`
   (легальные ходы генерит Gera.Chess по FEN доски — та же либа, что в грейне; имя игрока = его sub, чтобы
   по доске знать, кто ходит). Измеряет горячий путь ИГРЫ: ходов/с и задержку `MoveAsync` при N/2 партий
   в одном турнире (single-writer).

## Что считать деградацией
- Сценарий 3: p99 пробы приближается к бюджету тика (500 мс) — грейн не успевает вести партии.
- Сценарий 1: время регистрации N участников растёт квадратично (см. падение join ops/с с ростом N).
